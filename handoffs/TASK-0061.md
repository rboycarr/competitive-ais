## Objective
P1-31b, the second slice of P1-31. PO decision O31 (2026-11-03):
- `source.manage` holders suspend and retire sources;
- reinstating sends the source back to policy review, so a director who did not propose it approves a new policy version (P1-31a's `SourcePolicyService`);
- each change keeps a reason code and a required note in an append-only history.

What changed:
- **Schema** (`modules/Sources/database/migrations/2026_11_17_000100_create_source_status_changes_table.php`):
  - **`source_status_changes` table:** grant class `append_only`, added to `config/database.php`.
  - **`source_status_changes_transition_check`:** holds each step (action, from status, to status) and the reasons it allows:
    - suspend: approved → suspended;
    - reinstate: suspended → policy_review;
    - retire: any status but retired → retired.
  - **Note:** must not be blank.
  - **Rollback:** refused while history exists.
- **`SourceLifecycleService::change`:**
  1. checks `source.manage`;
  2. validates the action, reason and note, with validation errors for direct callers;
  3. locks the source row, then checks visibility (404 if hidden) and the status;
  4. writes the history row and moves the source;
  5. audits `source.suspended`, `source.reinstated` or `source.retired` (from status and reason only).
- **HTTP and page:**
  - `POST /sources/{source}/status` (`can:source.manage`);
  - the source page has a "Change status" form offering only the allowed steps and reasons, and a status history;
  - "Policy in force" reads "None (version n was approved; the source is …)" unless the source is approved.
- **`current_policy_id`:** keeps the last approval while the source is suspended or retired. Only an `approved` source may be used, which P1-37 enforces for evidence capture.

## Review focus
1. **Can a suspended or retired source become usable without a new independent approval?** Look at:
   - reinstate followed by decide (the proposer rule);
   - a rejected re-review: it goes back to `proposed` with the old `current_policy_id`;
   - every path that changes `status`.
2. **Schema and grants:**
   - the transition CHECK, and whether the database should also hold the source's own status transitions (documented as P1-52 hardening);
   - the append-only grant;
   - the rollback.
3. **Concurrency:** the lock order with `SourcePolicyService`; parallel suspensions; reinstate against retire.
4. **Validation and output:** the reasons per step, the note limits, how the history is rendered.
5. **Tests:** gaps in `SourceLifecycleTest`, the new `SourcePolicyConcurrencyTest` method and `Sources.test.ts`. Please mark anything that is not a merge blocker as such.
