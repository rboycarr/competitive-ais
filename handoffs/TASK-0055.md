## Objective
Verify the fixes for the TASK-0054 findings (disposition in `handoffs/TASK-0054-review.md`):
- **High (Pennant writes in the migrator service bypass the audit):** a flag is on only when its stored value is `true` **and** its last `feature.switched` audit row says on.
  - `Features::enabled()` makes one lookup on `audit_events`, using its `(action, occurred_at)` index, and only when the stored value is on.
  - `matchesAuditTrail()` backs `feature:status`, which shows "Matches audit trail" and exits 1 on a mismatch.
  - `switch()` also proceeds when the stored value already equals the target but the audit trail disagrees, so the command repairs an unaudited change with an audited one.
- **Medium (no database-backed Sources flag test):** new `SourceCollectionFlagTest` (DatabaseMigrations) uses the real table and the command.
  - `SourceTest` keeps the value-rule cases in Pennant's in-memory store, and now records the audited "on" switch inside its test transaction.
- **Low (concurrency test cache):** the cache is flushed before the final check, and the stored JSON is asserted directly.
- **Critical (outside the branch):** reported to the PO. AGENTS.md now forbids opening `.env`, `.env.*` other than `*.example`, and `.secrets/`.

## Review focus
1. Is each TASK-0054 finding resolved?
2. **The audit-trail rule:**
   - correctness of the JSON path query (`context->flag`) on MySQL 8.4;
   - ordering by `id`;
   - behavior when audit rows are written on another connection or in a transaction that has not committed yet;
   - cost per request;
   - anything an attacker with only the app account could do with it. The app account can INSERT into `audit_events`: could it forge an "on" row? (The stored value would still be `false`, since the app cannot write `features`.)
3. The repair path in `switch()` and the `feature:status` exit code.
4. Test gaps.
