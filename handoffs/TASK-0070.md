## Objective
P1-32b, the second slice of P1-32 (`handoffs/TASK-0069.md`). It completes the evidence pipeline P1-32a started: scans a quarantined asset, and either promotes clean bytes to content-addressed, locked storage or rejects the asset. PO decisions (2026-11-03): O33, 30-day default retention; O34, a scan-time type mismatch is rejected outright, never re-quarantined.

**What changed, by area:**

- **Scanner** (`modules/Platform/src/Scanning/ClamAvClient.php`): an in-house clamd `INSTREAM` client (ADR-0003: no package). Streams length-prefixed chunks over TCP; reads one reply; matches only `stream: OK` or `stream: … FOUND` exactly at the end of the driver's own message (`PDOException::errorInfo[2]`, never the wrapping exception's full message, which also carries the SQL-adjacent text some drivers append — not applicable here, but the same discipline as `Modules\Platform\Database\UniqueViolation` from TASK-0067). Any other reply, a connection failure, or a read timeout is a `RuntimeException`, which the caller treats as a retryable scan error, never a verdict.
- **Storage** (`modules/Platform/src/Storage/LockedObjects.php`): writes a blob **once**, with its object-lock retention on that same write, since Flysystem cannot pass lock parameters and a write-then-lock sequence would leave an earlier version unprotected. On the S3 adapter it calls the AWS SDK's `upload()` directly with an empty ACL (consistent with `PrivateBucketVisibility`, P1-32a) and governance-mode lock parameters; on any other disk (test fakes) it falls back to a plain write and returns no version ID.
- **Schema** (`modules/Evidence/database/migrations/2026_11_19_000100_create_evidence_blobs_table.php`): `evidence_blobs` (grant class `no_delete`), CHECKs for the hash format, a positive size, a non-blank MIME type, and the integrity status. `evidence_assets.evidence_blob_id` is added with `evidence_assets_blob_check`: exactly when `status = 'available'`. Rollback refused while any blob exists.
- **`EvidenceScanService`** (`modules/Evidence/src/Actions/EvidenceScanService.php`): claims an asset under a row lock only from `quarantined` with a pending (or `error`, reset to pending) scan; stages the quarantine object to a private temp file and checks its size; scans it; re-detects the type and rejects a mismatch outright; stores clean bytes once (reusing an existing blob for identical bytes); writes the result under the same row lock, so a terminal result is never overwritten and a duplicate or retried job is harmless; deletes the quarantine object afterwards, logging `evidence.quarantine_orphan` on a failed delete, as P1-32a does for uploads.
- **`ScanEvidenceJob`**: queue `evidence` (Horizon supervisor added), unique per asset, 3 tries, backoff 30/120/600 s, a `failed()` log entry after the last try.
- **`EvidenceUploadService`**: the scan dispatch moved **outside** the cleanup boundary. In the branch as Codex left it, a dispatch failure after the upload's transaction had already committed would still run the orphan-cleanup path and delete the just-uploaded file out from under its own (already saved) database row. It is now a separate `try`/`catch` that only reports a dispatch failure; the upload itself is unaffected, and the scan queue's own retry/claim logic picks the asset up later regardless.
- **Config:** the scanner's connection moved to `config/services.php` (`clamav`); `config/evidence.php` keeps only `blob_retention_days`. `compose.yaml` raises ClamAV's `StreamMaxLength` to 60M (the image's 25M default is below the 50 MB evidence limit).
- **Tests:** `EvidenceScanTest` (rewritten against the final service), `ClamAvClientTest` (new: a fake clamd forked for one connection, matching `Tests\Support\Concurrently`'s fork-safety convention), `PrivateObjectStorageTest` (extended for `LockedObjects`), `EvidenceUploadTest` (the dispatch-boundary fix, with a test forcing `Illuminate\Contracts\Bus\Dispatcher::dispatch()` to throw and asserting the already-committed asset and its quarantine object survive).

## A finding worth your attention
The automated EICAR test does not write the genuine 68-byte EICAR string to disk. An earlier version of that fixture (4 bytes short of the canonical string, from Codex's draft) went undetected by the real ClamAV while every automated test still passed, since they all mock the scanner. After correcting the fixture to the genuine string, the automated test started failing: Windows' real-time antivirus protection, scanning the NTFS volume the repository sits on (reached through WSL), blocks *reading back* a file holding the real signature (`file_exists()` succeeds; `readStream()` throws `UnableToReadFile`), even though the write itself succeeds. This reproduced on 3 isolated reruns. The automated test (`EvidenceScanTest::test_the_exact_standard_eicar_fixture_is_rejected_as_infected`) now uses a safe placeholder, since the scanner is mocked and never reads the bytes anyway; `test_the_eicar_fixture_decodes_to_the_genuine_signature` proves the constant itself is correct without touching disk. The genuine string was confirmed detected by the real local ClamAV over an in-memory stream (`php://memory`, never a file): `clean verdict: clean`, `eicar verdict: infected`.

## Review focus
1. **Fail-closed scanning:** can any path reach `available` without both a real `clean` verdict from `ClamAvClient` and a matching detected type? Check `claim()`'s status/scan_status gating, `decide()`'s row lock and the "only from pending" guard, and the reply-parsing in `ClamAvClient::verdict()`.
2. **The dispatch-boundary fix:** confirm the scan-job dispatch cannot, on failure, delete or otherwise affect an asset whose upload transaction already committed (`EvidenceUploadTest::test_a_failed_scan_dispatch_does_not_undo_an_already_committed_upload`).
3. **Idempotency and concurrency:** a duplicate or retried `ScanEvidenceJob` (same asset ID); two assets with identical content (one blob, reused); `evidence_assets_blob_check` and the blob migration's CHECKs.
4. **Object lock and storage:** `LockedObjects::write()`'s ACL and lock parameters against the SDK's `upload()` semantics; the plain-write fallback for non-S3 disks; whether anything here could let a blob be written without its retention.
5. **ClamAV client correctness:** the INSTREAM framing (length-prefixed chunks, zero-length terminator), timeout handling, and that every non-`OK`/non-`FOUND` outcome is treated as an error, never silently as clean.
6. **Tests:** gaps in `EvidenceScanTest`, `ClamAvClientTest`, `PrivateObjectStorageTest`, `EvidenceUploadTest`. Please mark anything that is not a merge blocker as such.
