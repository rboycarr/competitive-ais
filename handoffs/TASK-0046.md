## Objective
Show that registry rules hold under truly parallel requests (docs/11 P1-25, docs/09 item 14). The generated-key unique indexes and the locked relationship overlap check already exist (P1-21 to P1-23); this story adds the tests.
- **`tests/Support/Concurrently.php`:**
  - forks one process per task;
  - the parent first closes every database connection, so no socket is shared (cache, session and queue are in memory in tests);
  - all tasks start at one instant;
  - each child reports "ok" or its exception class through a temporary file, then ends with SIGKILL, so the parent's shutdown handlers don't run.
- **`RegistryConcurrencyTest`** (committed data, so `DatabaseMigrations`), 3 rounds × 4 parallel requests per scenario:
  - one winner for differently spelled duplicates: alias, own brand, top-level region, top-level category;
  - overlapping open-ended relationships;
  - crossing category moves (A under B, B under A, C between them), followed by `CategoryTree::inconsistencies()`;
  - removal guards against parallel use: brand removal vs. product creation, tag removal vs. tagging, currency decimal places vs. new markets (checked through audit event order);
  - in every scenario, each request ends in success or a `ValidationException`, never a database error.
- **Mutation check:** without the relationship locks, all 4 overlapping requests succeeded in round 1.

## Review focus
1. **Harness soundness:**
   - Can forked children share or corrupt the parent's state: connections, open transactions, files, the PHPUnit process?
   - Is SIGKILL safe?
   - Can a child that never reports make a test pass wrongly?
   - Does the start barrier give real overlap?
2. **Invariants:** are they correct and strong enough? In particular:
   - the brand and tag either-or checks;
   - the currency check by audit event order (are auto-increment IDs a valid order here?);
   - the category check.
   Can any scenario pass vacuously?
3. **Gaps:** registry races not covered that matter now; services using a single transaction attempt where a deadlock is plausible.
4. **Isolation:** does the committed data leak into other tests (`DatabaseMigrations` rollback and the base `TestCase` reset)? What about CI time and flakiness?
