## Objective
Reference data for markets (docs/11 P1-23a, docs/02 §3.3 and §6, docs/03 Registry; PO decision O28). `currencies`: ISO 4217 subset seeded by its migration, in a **new grant class `read_only`** (SELECT only for the app; `TableGrants`, `ApplyDatabaseGrants`, config, probe and data-driven tests in `DatabaseAccountsTest`). `markets`: fixed upper-case code, ISO country, default currency FK, `no_delete`. `regions`: a tree per market whose levels deepen strictly (region › province › city › district), held by the database: generated `level_rank`, a stored `parent_level_rank`, the composite foreign key (parent_id, market_id, parent_level_rank) → regions (id, market_id, level_rank) and `regions_parent_check`. `MarketService` / `RegionService` need `taxonomy.manage`. Admin › Markets pages.

## Review focus
1. Grants: is the `read_only` class correct and fail-closed (plan, apply, verification, the "two classes" and "unclassified" checks)? Can the app write to `currencies` in any way? Is it right that the migration (as the migrator) seeds the table?
2. Region integrity: can any write (service or direct) produce a parent in another market, a child not deeper than its parent, a cycle, or a parent whose level changes under its children? Are the generated column, the nullable rank and the CHECK/foreign-key interplay sound on MySQL 8.4?
3. Authorization: `taxonomy.manage` on routes and services; regions reached only through their own market.
4. Audit: context without user input (market codes and names are not in the context), no events for no-ops.
5. Frontend: text rendering, levels offered under a parent, `parent: null` for the top level.
