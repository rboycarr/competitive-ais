## Objective
Find defects that would let the application account (or anything running as it) change or delete append-only data, change the schema, read data it should not, or gain privileges. The same applies to the object-store keys and the CI pipeline.

## Review focus (priority order)
1. **Privilege escalation through the migrator.** The migrator holds its schema privileges `WITH GRANT OPTION` so `db:apply-grants` can run without root. Can that, or the automatic connection switch, be abused from application code paths (web requests, queued jobs, the scheduler)?
2. **Grant correctness.** `GRANT` then `REVOKE IF EXISTS … IGNORE UNKNOWN USER` per table. Windows where privileges are missing or excessive; tables created outside migrations; dropped/renamed tables leaving stale `tables_priv` rows; views; behaviour when `config('database.grants')` lists a table that does not exist yet.
3. **Init script safety.** Values are inlined into SQL after validation. Is the validation sufficient? Is the script idempotent and safe on an existing volume? Anything left from the interim single-account layout?
4. **Test adequacy.** Do the tests really prove "UPDATE/DELETE fail on append-only tables and every required INSERT succeeds" (`docs/11` P1-09)? The real append-only tables do not exist yet; probe tables are used. What is missing?
5. **Object-store keys.** The app identity has `Read/Write/List/Tagging` on three buckets plus retention and legal-hold get/put on `evidence`, and no `BypassGovernanceRetention`. Can it delete locked versions or touch `audit-anchor` another way? Is rendering keys into `/tmp/s3.json` inside the container acceptable?
6. **CI.** Token scope, action pinning, secrets handling, `pull_request` from forks, the gitleaks exemption for `.env*.example`, and whether a failing check can be bypassed.
