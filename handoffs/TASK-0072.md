## Objective
P1-33: "Same bytes → one blob, two assets with their own source/capture data".

The de-duplication itself shipped with P1-32b (merged as pull request #31):
- one `evidence_blobs` row per SHA-256;
- an atomic insert-or-reload, under a per-hash named lock;
- each asset points at the shared blob through `evidence_blob_id`.

This story adds no application code and no schema change. It adds one test that the sharing never merges provenance:
- `EvidenceScanTest::test_shared_bytes_keep_each_assets_own_provenance`
  - Two uploads of the same bytes go through `EvidenceUploadService`, by different uploaders, with different titles, sources, capture times and classifications. Both are then scanned.
  - The result is one blob and one stored object.
  - Each asset keeps its own fields.
  - Each asset has its own custody trail: `uploaded` by its uploader, then `scanned` by the system.
  - Each asset has its own audit records.
  - A reader with Internal clearance sees only the Internal asset. Sharing a blob never widens visibility.

Showing in the UI that a file is shared waits for the evidence detail page (P1-34).

## Review focus
1. Is there any path where one asset's provenance, custody or visibility depends on another asset that shares its blob? Look at `EvidenceScanService` and `EvidenceAsset::seenBy`.
2. Does the test prove what it claims, or could it pass with provenance merged? For example, check the ordering assumptions and the audit query by `subject_ulid`.
3. Is anything in the P1-33 acceptance line still undelivered?
