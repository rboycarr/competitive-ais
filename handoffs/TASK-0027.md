## Objective
Auditors (and other `audit.view` holders) search the audit trail read-only by actor, action, subject and time range (docs/11 P1-16). Audit rows carry the classification of their subject at event time, so they are filtered by `AccessScope` like any record (ADR-0005: no other code decides visibility): an auditor needs a restricted grant to see restricted rows. Network data (IP address) is personal data kept apart (`audit_event_network`) and is not shown. Each search is itself audited.

## Review focus
1. Read-only guarantee: can anything in this branch change, delete or forge audit rows (read model, routes, GET handler)? Does the new index migration risk the hashes or checkpoints?
2. Visibility: are audit rows filtered correctly (clearance, restricted rows need a grant, inactive accounts), and can a filter or the cursor bypass `visibleTo`?
3. Data exposure: what reaches the browser (context, actor names, subject types, request IDs)? Should anything be withheld?
4. Input handling: ULID, action and date filters, time zones, cursor tampering, query cost on a large table.
5. The `audit.searched` record: right actor and context, no user input recorded, transaction use.
