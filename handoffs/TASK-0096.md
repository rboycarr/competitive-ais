## Objective
P1-50: "As an auditor, audit tampering is detectable even by someone with DB access". Acceptance (docs/11): lag-windowed checkpoints; Ed25519-signed manifests exported to the audit-anchor bucket; verification against the exported manifests; `late_commit` handling (supplementary checkpoints); business-transaction duration capped below the lag window and monitored, with an alert (TASK-0010 #4); key-rotation runbook. Threat T21 (docs/07).

PO decisions (2026-11-07, docs/11):
- **O43.** A new `auditor` Compose service is the only holder of the signing seed (`.secrets/signing.env`) and the audit-anchor key (`.secrets/anchor.env`, shared with SeaweedFS, which must verify request signatures).
- **O44.** Manifests are locked in COMPLIANCE mode for 2557 days in production (enforced in code), GOVERNANCE for 1 day locally and in CI.
- **O45.** Checkpoints closed before P1-50 are signed after checking each against its rows, in the same generation.

## Changes
- **Schema** (`modules/Platform/database/migrations/2026_11_29_000100_anchor_audit_checkpoints.php`):
  - `audit_checkpoints.revision` (default 1) and `supplements_id` (self FK, RESTRICT); CHECK `revision >= 1 AND (revision = 1) = (supplements_id IS NULL)`. Unique keys move to `(generation, from_audit_id, revision)` and `(to_audit_id, revision)`.
  - `audit_anchors` (append-only grant class): checkpoint_id UNIQUE FK, key_id, signature (hex), object_key UNIQUE, manifest_sha256, anchored_at; hex CHECKs. The signature is recorded here, not on the checkpoint row as docs/02 first specified, because checkpoint rows cannot be updated after their export.
  - `down()` refuses while a supplementary checkpoint exists.
- **`AuditSigner`:** Ed25519 via sodium from a 32-byte hex seed (`audit.anchor.signing_seed`); key ID = first 16 hex of SHA-256(public key); trusted keys = the current key plus `AUDIT_TRUSTED_KEYS` (earlier public keys). The secret key is zeroed after signing.
- **`AuditAnchor`:**
  - `checkpoint()`: fails first if there is no key or the lock mode is wrong (so nothing is closed that cannot be signed), exports pending checkpoints, closes the next range (`AuditCheckpointer`, unchanged apart from the unique-key names), exports it.
  - `anchorPending()`: every checkpoint of the generation with no anchor row and no supplement, in ID order. Before signing, the range's rows are re-read: any row whose hash fails, or a count or root that differs, stops the run with an exception; nothing is signed.
  - Export: manifest (fixed field order) → signature over its compact JSON → object `{"manifest", "signature"}` written once with its object lock (`LockedObjects::write`, new `$mode` parameter) → `audit_anchors` row. A unique violation on the anchor row (concurrent run) is ignored; Ed25519 is deterministic, so the bytes are the same.
  - `reanchor(from, reason)`: reason required; latest revision for the range; refused if any row fails its hash or the count is not greater than counted; inserts revision + 1 with `supplements_id`, records `audit.reanchored` (system actor, context includes the reason as `text`) in the same transaction, then exports.
- **`AuditVerifier`** (rewritten): lists `g<generation>/` in the bucket, checks each object's structure, signature (trusted keys only) and name; the highest valid revision per range is authoritative. Reports `manifest_invalid`, `chain_gap`, `late_commit`, `rows_missing`, `root_mismatch`, `row_tampered` against the manifests; `checkpoint_missing`, `checkpoint_mismatch`, `manifest_missing` comparing the DB to the manifests; `unanchored` and `anchor_stale` (high) after 30 minutes. `verifyAndReport()` logs critically and raises `AuditVerificationFailed`.
- **Commands:** `audit:checkpoint` (close + sign + export), `audit:verify` (exit 1 on issues), `audit:reanchor {from} --reason=`, `audit:work` (the auditor's loop: checkpoint every 300 s, verify hourly, SIGTERM between runs, `--once`). The queued `CreateAuditCheckpointJob` and `VerifyAuditChainJob` are removed: the scheduler and Horizon hold no key.
- **Transaction cap:** `TransactionDurationMonitor` (listeners on transaction begin, commit and rollback; outermost transaction per connection) logs `Long database transaction committed` critically above `audit.transaction_alert_seconds` (300). FPM `request_terminate_timeout = 120s`; Horizon timeouts are 60 and 120 s.
- **Infrastructure:**
  - `compose.yaml`: `auditor` service (the app image, `data` network only, `env_file` anchor + signing, GOVERNANCE/1 day). SeaweedFS also reads `anchor.env`.
  - `.env.anchor.example`, `.env.signing.example`; the anchor key leaves `.env.s3.example`. `init-env.sh` moves existing values and generates the 32-byte seed; scenario 6 in `init-env-test.sh`.
  - `scripts/ci/backend.sh` checks with `compose config` that only `auditor` gets `AUDIT_SIGNING_SEED`, only `auditor` and `seaweedfs` get `S3_ANCHOR_ACCESS_KEY`, and only `seaweedfs` and `seaweedfs-init` get `S3_ADMIN_ACCESS_KEY`.
  - `docker/seaweedfs/s3-identities.template.json`: the anchor identity gains `GetObjectRetention` and `PutObjectRetention` on `audit-anchor` only. Found live: SeaweedFS refuses a PutObject with lock headers without it (the fake disk could not show this).
  - `verify-object-store.sh`: K19–K22 (the anchor key writes a locked manifest and can neither delete it, bypass governance, nor shorten its retention; K20–K22 fail outright if K19 wrote nothing).
- **Docs:** docs/01, 02 (as built), 07 (T21), 10 (env files, services, alerts, the §6 runbooks for late commits, incidents, failures and key rotation), 11 (O43–O45, P1-50), ADR-0006 "As built".

## Review focus
1. **T21:** can someone with database write access (including the migrator account), but without the seed and without delete rights on the bucket, change, add or remove audit rows inside a signed range without a critical finding? Consider edits to `audit_checkpoints` and `audit_anchors`, a deleted anchor row, an added fake checkpoint or revision, and generation changes.
2. **Signing before checking:** can a tampered or late-committed range be signed, by `anchorPending` (including the O45 back-signing), or by `reanchor` (a forged row with a valid recomputed hash plus extra rows)? Is the reanchor guard as strong as it can be without the old leaf list?
3. **Manifest trust:** is the parsing in `AuditVerifier::signedManifest` strict enough (types, key order, a re-encoding difference that makes a genuine manifest fail)? Can a manifest from another generation, or an object named for one range but signed for another, be accepted?
4. **Key isolation:** do the web, Horizon and scheduler containers reach the seed or the anchor key in any way (env, bind mount, `compose config` output in CI logs)? Is the CI check sound?
5. **Failure modes:** an export that succeeds while the anchor-row insert fails; a concurrent manual `audit:checkpoint` and `audit:work`; the store being down; the auditor being down (`anchor_stale` is reported only by the auditor itself).
6. **Transaction monitor:** is measuring at commit (not killing) an acceptable "cap and monitor", given that FPM and Horizon cut off requests and jobs? Can the listeners misbehave with nested transactions, savepoints or `RefreshDatabase`?
7. **Migration:** the unique-key swap, the CHECK, and `down()`; anything unsafe for the CI migrate → reset → migrate round trip.
