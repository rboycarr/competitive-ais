Each module lists its responsibility, public contracts (what other modules may use), domain events, permissions, routes, and phase. Internal classes are private to the module (enforced by Pest `arch()` tests).

## Platform (shared kernel) — Phase 1
- **Provides:** `Classification` enum (ordered: public < internal < confidential < restricted); `HasPublicUlid` trait; `AccessScope` (§Identity); `AuditLogger::record(action, subject, context)`; `OutboxPublisher::publish(aggregate, eventType, payload)`; Money and Quantity value objects; `ProblemDetails` exception rendering (RFC 9457); `RequestId` middleware; security-headers middleware (CSP nonce, nosniff, frame-ancestors).
- **Rules:** `AuditLogger` and `OutboxPublisher` must be called inside the caller's DB transaction. Context keys are allowlisted per action.
- **Jobs:** `RelayOutboxJob`, `CreateAuditCheckpointJob` (scheduled), `VerifyAuditChainJob` (scheduled, alerts on mismatch).

## Identity (M01) — Phase 1
- **Responsibility:** authentication (Fortify), MFA, invitations, users, teams, roles/permissions (spatie), access grants, API tokens (Sanctum), session management.
- **Contracts:** `AccessScope` interface (implemented here, bound in the container):
  - `allows(User, Classifiable&Scoped $record): bool`
  - `applyTo(Builder $query, User): Builder` — the Eloquent scope `visibleTo($user)`
  - `searchFilter(User): string` — Meilisearch filter expression [P2]
  - `vectorFilter(User): array` [P4]
  - `effectiveGrants(User): GrantSet` (cached per request)
  - **Implemented (P1-15, 2026-11-01):** the interface, `Classifiable`, `Scoped`, `GrantSet` and the `VisibleTo` trait (`visibleTo($user)` scope) are in `Modules\Platform\Access`; `Modules\Identity\Access\GrantAccessScope` implements it and is bound per request (scoped binding). The interface takes `Authenticatable` (Platform cannot depend on Identity's `User`); any other user type, and any inactive account, sees nothing. Also `ensureVisible()` (404 for hidden records) and `forget()` (the grant and team actions clear the per-request cache). `searchFilter` and `vectorFilter` come with Phase 2 and Phase 4; record status (drafts) with the intelligence items. Models declare their scope pivots through `Scoped::scopeRelations()` and keep the classification in a `classification` column.
- **Events:** `UserInvited`, `UserActivated`, `UserSuspended`, `RoleAssigned`, `RoleRevoked`, `AccessGrantCreated`, `AccessGrantRevoked`, `MfaEnabled`, `MfaReset`, `LoginSucceeded`, `LoginFailed`.
- **Permissions:** `user.view`, `user.manage`, `team.manage`, `role.manage`, `grant.manage`, `audit.view`, `token.manage`.
- **Rules:** invitations only (no self-registration). MFA is required for any role that holds `user.manage`, `role.manage`, `grant.manage`, `intelligence.publish`, `source.approve`, or `export.run`. `EnsureMfa` middleware blocks access until MFA is enrolled. A user cannot raise their own clearance or grants.
- **Pages:** Login, MFA challenge/enroll, Accept invitation, Profile & security (sessions, MFA, tokens), Admin › Users, Teams, Roles, Access grants.

## Registry (M02, M03, M04) — Phase 1
- **Responsibility:** competitors, aliases, relationships, brands, categories, products (competitor or own), variants, markets, regions, channels, retailers, currencies, tags.
- **Contracts:** `CompetitorLookup` (find by ULID or alias, `visibleTo` aware), `ProductLookup`, `MarketLookup`. Read DTOs only; other modules never write registry tables. Uses Identity's `UserDirectory` contract (active permission holders and display names as `UserSummary`, never the `User` model; P1-20). `CompetitorLookup` implemented (P1-20a): `findVisible`, `visibleTo`, `summaries`, always filtered by `AccessScope`, returning `CompetitorSummary`; Identity uses it for competitor-scoped grants. `MarketLookup` implemented (P1-23c): `find`, `all`, `summaries`, returning `MarketSummary` (markets are unclassified, so no viewer filter); Identity uses it for market-scoped grants.
- **Events:** `CompetitorCreated`, `CompetitorUpdated`, `CompetitorArchived`, `ProductCreated`, `ProductUpdated`, `VariantCreated`.
- **Permissions:** `competitor.view`, `competitor.manage`, `product.view`, `product.manage`, `taxonomy.manage`.
- **Rules:** archiving is blocked while open (non-terminal) intelligence items reference the entity; it warns otherwise (competitors: implemented in P1-40, `CompetitorService::setLifecycle` checks `IntelligenceReferences` under the competitor's row lock). Relationship validity ranges must not overlap for the same pair and type. Aliases are normalized (trim, collapse whitespace) and stay unique per competitor. Implemented in P1-21 (`CompetitorAliasService`, `CompetitorRelationshipService`; docs/02 §3.3): aliases are unique ignoring case and accents; a relationship is visible and changeable only for viewers who can see both competitors; the overlap check runs under locks on both competitor rows. Lookup by alias is added to `CompetitorLookup` with its first consumer (quick search, P1-24). Brands and the category tree implemented in P1-22a (`BrandService`, `CategoryService`): a competitor's brand follows the competitor's visibility (O25); categories are maintained by `taxonomy.manage` holders. Products and variants implemented in P1-22b (`ProductService`, `VariantService`, `ProductAccess`): visible like competitors (O25); `ProductLookup` is added with its first consumer. Currencies, markets and regions implemented in P1-23a (`MarketService`, `RegionService`; Admin › Markets); `MarketLookup` implemented with its first consumer (market grants, P1-23c). Channels, retailers and tags implemented in P1-23b (`ChannelService`, `RetailerService`, `TagService`, `CompetitorTagService`; currencies editable by taxonomy managers through `CurrencyService`, PO decision O29): competitor managers tag the competitors they can see; a tag, channel or retailer in use is kept.
- **Pages:** Competitors (list with filters for lifecycle, tier, analyst, tag; detail tabs Profile, Aliases, Relationships, Products, Intelligence, Evidence, Activity), Products (list, detail, variants), Admin › Markets, Regions, Currencies, Channels, Retailers, Categories, Tags.

## Sources (M06, M07) — Phase 1 (manual) / Phase 3 (automated)
- **Responsibility:** source registry, ownership, versioned policy decisions, lifecycle. Phase 3 adds schedules and health.
- **Contracts:** `SourceRegistry::isApprovedFor(Source, Method): bool` (used by Evidence now and Collection later); `SourceReliability`.
- **Events:** `SourceProposed`, `SourcePolicyDecided`, `SourceApproved`, `SourceSuspended`, `SourceRetired`.
- **Permissions:** `source.view`, `source.propose`, `source.approve` (Director), `source.manage`.
- **State machine:** proposed → policy_review → approved | rejected(→ proposed after edit); approved → suspended → approved | retired. Each decision appends a `source_policies` version.
- **Rules (Phase 1):** `method` must be `manual` while the `collection` flag is off. The proposer cannot approve their own source. Proposing implemented in P1-30 (`SourceService`; docs/02 §3.4): sources are classified records without scopes, visible through `AccessScope`; the owner must be an active `source.propose` holder who can see the source. The policy review implemented in P1-31a (`SourcePolicyService`; docs/02 §3.4): the owner or proposer submits (`proposed` → `policy_review`); a director (`source.approve`, two-factor, not the proposer; PO decision O9) records a new policy version: approved puts it in force, rejected and needs-info return the source to `proposed` (PO decision O30). the contract arrived with its first consumer as **`SourceLookup`** (P1-37, in place of `SourceRegistry::isApprovedFor`: evidence needs the policy version in force, not a yes/no): `usableBy` (approved sources the viewer can see), `forCapture` (a source by ULID with its policy in force, optionally under a share lock on the source row) and `recorded` (a source and the approved policy recorded on a capture), each filtered by `source.view` and `AccessScope` and returning `SourcePolicySummary`; method-specific approval comes with collection (Phase 3); suspend, reinstate and retire implemented in P1-31b (`SourceLifecycleService`, `source.manage`; PO decision O31): a reinstated source goes back to policy review, retiring is final, every change has a reason code and a note in the append-only history.
- **Pages:** Sources (list, detail with policy history), Policy review form.

## Evidence (M09) — Phase 1
- **Responsibility:** upload, quarantine, malware scan, hashing, content-addressed storage, custody, downloads, legal hold, retention metadata.
- **Contracts:** `EvidenceReader::find(ulid, User)` (authorization-aware, returns a DTO); `EvidenceLinkGuard::assertLinkable(asset)` (must be `available`).
- **Events:** `EvidenceUploaded`, `EvidenceScanned`, `EvidenceRejected`, `EvidenceDownloaded`, `EvidenceScopeInherited`, `EvidenceWithdrawn`, `EvidenceIntegrityCompromised`, `LegalHoldSet`, `LegalHoldReleased`.
- **Jobs:** `ScanEvidenceJob` (queue `evidence`, unique per asset, 3 tries, backoff 30/120/600 s), `VerifyEvidenceIntegrityJob` (scheduled sample re-hash).
- **Permissions:** `evidence.view`, `evidence.upload`, `evidence.download`, `evidence.hold`.
- **Rules:** MIME allowlist (PDF, PNG, JPEG, WebP, plain text, CSV, DOCX, XLSX — configurable); size cap of 50 MB (configurable); the filename is sanitized and never used as a storage key.
- **Source policy at capture** (TASK-0001 #5): if the upload names a source, that source must be `approved`, and the asset records `source_policy_id` = its current approved policy version. Uploads without a registered source are allowed for manual evidence (e.g., an analyst's own photo) and are labelled "unregistered source" in provenance. Whether to forbid them was Product Owner question Q3 (decided O12: allowed). Implemented in P1-37 (docs/02 §3.5): the policy in force is read again under a share lock on the source row in the upload's transaction, so a suspension or a new decision lands wholly before or after the capture; the detail page shows the source and policy version (or a placeholder when the viewer cannot see the source).
- **Scopes** (TASK-0001 #1): the uploader declares competitor/market scopes (optional; an unscoped asset is visible to anyone whose clearance meets its classification). Linking to a claim inherits the item's subjects (all-of semantics, `docs/07` §3).
- **Evidence state after publication** (TASK-0001 #10): if a linked asset is withdrawn or fails an integrity check, an `EvidenceIntegrityCompromised` / `EvidenceWithdrawn` event flags every approved or published item that cites it for re-review. Nothing is auto-retracted. Legal hold never affects readability. **Implemented in P1-48** (as the outbox events `evidence.withdrawn` and `evidence.integrity_failed`): **withdrawal** (`EvidenceWithdrawalService`, `POST /evidence/{asset}/withdraw`): `evidence.hold` (directors; no separate permission), an asset the actor sees (404 otherwise), available and not on legal hold (release it first), a reason (as for holds, at most 1,000 characters, kept in the custody trail, never in the audit context); final. Under the asset's lock, then the blob's: the asset becomes `withdrawn` and lets go of its blob (`evidence_assets_blob_check`), so it is never served or cited again; the blob and its stored version are kept under their own retention (no deletion: O38's deleting job is still to come); a `withdrawn` custody event (reason and the blob's SHA-256), `evidence.withdrawn` audited (SHA-256) and the outbox event, in one transaction. The page keeps showing the SHA-256 from the custody trail. **Integrity re-hash** (`EvidenceIntegrityService`, `evidence:verify-integrity --limit=50`, daily at 03:15 UTC): the blobs not yet marked, least recently verified first; the stored version is read outside any transaction (`LockedObjects::readVersion`: a missing object or version reads as missing, any other store error is raised and the blob left for the next run) and hashed; a match sets `last_verified_at`; a mismatch or missing object marks the blob `mismatch` for good, under the locks of its assets (ID order) and then the blob, with an `integrity_failed` custody event (system), `evidence.integrity_failed` audited (result, SHA-256) and the outbox event for each available asset on it. Such evidence is no longer downloadable, citable or counted as support (`EvidenceLinking`). The command exits 1 when any blob failed its check or could not be checked.
- **Dedupe** (TASK-0001 #7): the scan runs on the asset's quarantine object. Only clean bytes are promoted to a blob, with an atomic insert-or-reload on `sha256`. Blob retention and hold are the maximum and OR of all referencing assets, recomputed under lock. A blob object is deleted only by a job that rechecks for zero references and no retention or hold under lock. Implemented in P1-38 (docs/02 §3.5): per-asset `retention_until` from the source policy recorded at capture (O39: counted from the upload), blob retention extended to its longest-kept asset, `EvidenceBlobReconciler` with the daily `evidence:reconcile-blobs`, the `deletable()` check a future deleting job must pass (O38), and the hourly `evidence:sweep-quarantine`. Downloads are served as attachments through a pre-signed URL (TTL ≤ 60 s) after a policy check. Previews are images only, rendered from the evidence bucket through Laravel with `Content-Type` forced from `detected_mime`.
- **Implemented in P1-32a** (`EvidenceUploadService`; docs/02 §3.5): upload into quarantine with the type detected from the bytes, display-only file names, custody and audit in one transaction; until available, only the uploader and `evidence.hold` holders see an asset (PO decision O32). The scan, blobs and promotion follow in P1-32b.
- **Pages:** Evidence (list, upload, detail with metadata, hash, custody timeline, linked claims).
- **Contract (P1-41, P1-36b):** `EvidenceLinking` (`linkable`, `lockLinkable` and `lockSeen` with row locks for update and visibility from the current scopes, `inherit`, `summaries`, `recordLink`), seen as on the evidence pages: `evidence.view`, then `EvidenceAsset::seenBy`. Sources adds `SourceLookup::summaries` (`SourceSummary` with the default reliability).

## Intelligence (M10) — Phase 1 (core) / Phase 2 (contradictions, claim workflows)
- **Responsibility:** intelligence items, subjects, claims, evidence links, verification, publication, retraction, supersession, provenance trace.
- **Contracts:** `IntelligenceReader` (published, visibility-aware) for Dashboard, Battlecards, Reports, and AI.
- **Events:** `IntelligenceSubmitted`, `IntelligenceReviewed`, `IntelligencePublished`, `IntelligenceRetracted`, `IntelligenceSuperseded`.
- **Permissions:** `intelligence.view`, `intelligence.create`, `intelligence.submit`, `intelligence.review`, `intelligence.publish`, `intelligence.retract`.
- **State machine** (enforced in `IntelligenceStateMachine`, one Action per transition):

| From | Action | To | Guard |
|---|---|---|---|
| draft / changes_requested | submit | submitted | `intelligence.submit`; author or owner; ≥1 claim; every claim has ≥1 `supports` link to an `available` asset |
| submitted | assign / reassign | submitted | Director or queue owner; `reassign` review row + audit |
| submitted | start_review | in_review | `intelligence.review`; actor is the **assigned** reviewer; reviewer ≠ author |
| in_review | approve | approved | assigned reviewer; reviewer ≠ author; `approve` review row with `item_version` + `content_hash` |
| in_review | request_changes | changes_requested | assigned reviewer; rationale required |
| in_review | reject | rejected | assigned reviewer; rationale required |
| approved | publish | published | `intelligence.publish`; publisher ≠ author **and** ≠ approving reviewer; current-version approval with matching `content_hash` (`docs/02` §3.6), checked under row lock; Director role if classification ≥ confidential or `high_impact` |
| approved / published | flag_for_rereview | *(unchanged)* | system (evidence withdrawn or integrity failure) or Director; reason recorded; published items stay visible with a "Under re-review" banner until decided. **As built in P1-48 (PO decision 2026-11-07):** the status does not change (moving a published item to in_review would hide it from its readers); a `rereview_flags` row and `rereview_since` mark it, publication waits for the flag to be cleared (`clear_rereview`, a director with a reason, every claim still supported) or the item is retracted or replaced; flagging by a Director is not built yet |
| published | retract | retracted | `intelligence.retract`; reason required; retraction row |
| published | supersede | superseded | new item published with `supersedes_id` |

Item content (title, summary, claims, links, subjects) is **editable only in `draft` and `changes_requested`**. Every edit increments `version`. Approvals for earlier versions never count (TASK-0001 #3, #4). Concurrent edit/publish is serialized by the item row lock.

- **Pages:** Intelligence Feed (filters: status, type, competitor, classification, date semantics), Item editor (claims, evidence picker, locator/excerpt), Verification Queue (assignment, age, SLA), Provenance trace (item → claims → evidence → blob hash → source + policy version → custody → reviews → audit).
- **Implemented (P1-40, 2026-11-06):** module `Modules/Intelligence`. `IntelligenceItemService` (create, edit) and `IntelligenceClaimService` (add, edit, withdraw, move). Writing needs `intelligence.create`; content changes only while editable (draft, changes requested), only by the author or owner, from the version read (`version`, checked under the item's row lock: a stale form is refused), and every change raises the version. Subjects: competitors and products the writer can see, markets; at least one, at most 20 of each; archived competitors refused under a share lock on the competitor row. Nobody writes an item they could not read back (classification and every subject), lowering a classification needs `intelligence.publish`, and an item about a subject its editor can no longer see cannot be edited (the form would drop it). Claims: plain-text statement, type, and both Admiralty ratings chosen by a person, never defaulted (ADR-0010; source pre-fill comes with evidence links, P1-41); at most 50 active per item; withdrawn, never deleted. Visibility: `IntelligenceItem::seenBy` = AccessScope plus statusVisible (docs/07 §3): until released (published, retracted, superseded) only the author, owner, assigned reviewer and `intelligence.review` holders; hidden items are 404; subjects the viewer cannot see are counted, never named. The summary is shown through `Modules/Platform/src/Support/SafeMarkdown.php` (CommonMark with raw HTML escaped and unsafe links refused, then a tag/attribute allowlist; images become their alt text; links get `rel="noopener noreferrer nofollow"`), sent to the page as a node tree and rendered by `resources/js/Components/MarkdownView.ts` from its own tag list (no `v-html`). Audited with codes, counts and IDs only: `intelligence.created`, `intelligence.updated` (fields, version), `intelligence.claim_added` / `claim_updated` / `claim_withdrawn` / `claim_moved` (claim ULID, type, rating, version). Contract `IntelligenceReferences` (open items about a competitor) for the Registry archive guard. Pages: Intelligence (feed with filters and the new-item form), item page (summary, dates with their labels, subjects, claims with the rating badge, editor). Registry adds `ProductLookup` and `CompetitorLookup::lockUnarchived`.
- **Implemented (P1-41, 2026-11-06):** claims cite evidence (`IntelligenceClaimService::link` / `unlink`, same edit rules and version path as the other claim changes): an active claim; an `available` asset the writer can see, looked up and share-locked through the Evidence contract `EvidenceLinking::lockLinkable` (lock order: the item, then the asset); relation supports, contradicts or context, chosen, never defaulted; optional locator (single line, at most 255) and excerpt (plain text, at most 2,000); each asset and relation once per claim; at most 20 per claim. A link is removed, not edited, and only by someone who can see its asset. Audited as `intelligence.evidence_linked` / `evidence_unlinked` (claim ULID, evidence ULID, relation, version; at the higher of the item's and the asset's classification; never the locator or excerpt), and recorded as `linked` / `unlinked` custody events on the asset in the same transaction. The item page describes a citation (title, status, relation, locator, excerpt, the source's name and default reliability beside the claim's own rating, ADR-0010) only to viewers who can see the asset, and the source only to those who can see it; the others are counted. Evidence picker: available evidence the editor sees, searched by title (partial reload). Not yet: inherited scopes on link (P1-36b), the evidence page's citing claims (P1-45), re-review when cited evidence is withdrawn.
- **Implemented (P1-36b, 2026-11-06):** cited evidence inherits the item's competitors and markets as scopes (`EvidenceLinking::inherit`), when cited and when the editable item gains a subject; never removed; recorded in custody (`scope_inherited`) and audit (`evidence.scope_inherited`). Citing locks the asset for update and judges visibility from its current scopes (`lockLinkable`, `lockSeen`); nobody cites or edits their way out of seeing the evidence. Provenance hiding comes with the provenance view (P1-45); the item page already describes only evidence the viewer can see.
- **Implemented (P1-42, 2026-11-06):** `IntelligenceWorkflowService::submit` (the state machine's transitions live in this service, one method each): draft or changes_requested to submitted; an item the actor cannot see is 404 first (TASK-0087 #1; the route needs only `intelligence.view`), then `intelligence.submit`, the author or owner, from the version read; under the item's row lock. Guard as in the table above: at least one claim, and every claim not withdrawn (disputed included) has a `supports` link to an `available` asset, whoever can see it; the cited assets are share-locked after the item (`EvidenceLinking::available`, IDs only), so none is withdrawn or rejected meanwhile. Contradicting or context links do not count as support. The version does not change (no content changed); the item is frozen until changes are requested. Audited as `intelligence.submitted` (version, claim count). The item page shows its author or owner what still blocks submission (per claim) or the submit button. `IntelligenceSubmitted` is defined with its first consumer (the queue, P1-43).
- **Implemented (P1-43, 2026-11-06):** the verification queue (`/verification`, `VerificationQueueController`): submitted and in-review items the viewer sees (`IntelligenceItem::seenBy`), oldest submission first (`submitted_at`, shown as the time waiting), filtered by assignment (to me, nobody yet), status, classification, competitor and impact; for `intelligence.review` and `intelligence.publish` holders (403 otherwise; a Verification link in the menu). Transitions in `IntelligenceWorkflowService`, each one: a hidden item is 404 first, whatever the input (the input is validated by the service after the visibility check; the P1-42 submit action now does the same); then the permission; then, under the item's row lock, the guard. **assign**: a director (`intelligence.publish`; "queue owner" is not a separate role yet) names an active `intelligence.review` holder (read under a share lock on their row) who is not the author or owner and can see the item; a submitted or in-review item; the first is an `assign` row, a later one a `reassign` row with a required reason, and an in-review item goes back to submitted for the new reviewer. Reviewers do not take items themselves. **start_review**: submitted to in_review, by the assigned reviewer only. **decide**: approve, request changes or reject, by the assigned reviewer only, never the author or owner, from the version read; a reason (plain text, at most 5,000 characters) for requesting changes or rejecting, optional for approving; approval also needs every claim not withdrawn to have a `supports` link to available evidence *the reviewer can see* (`EvidenceLinking::availableSeen`, share-locked after the item), and sets `verified_at`. Requesting changes makes the item editable again; the reviewer stays assigned, and the resubmission restarts the age. Rejected is final. Every assignment and decision is an append-only `verification_reviews` row with the version and content hash (docs/02 §3.6), and is audited without user text: `intelligence.reviewer_assigned` (decision, reviewer ULID, review ULID, version), `intelligence.review_started` (version), `intelligence.reviewed` (decision, review ULID, version). The item page shows the reviewer, the submission and approval times and the review history (rationales included) to anyone who sees the item; the assign form to directors (eligible reviewers only), start and decide to the assigned reviewer, with what still blocks an approval; the decision is chosen, never preselected. Not yet: `IntelligenceSubmitted` and `IntelligenceReviewed` events and notifications (with their first consumer), the SLA, publication (P1-44), re-review flags (P1-48).
- **Implemented (P1-44, 2026-11-06):** `IntelligenceWorkflowService::publish` / `retract` and `IntelligenceItemService::draftReplacement`; routes `POST /intelligence/{item}/publish|retract|replacement` (only `intelligence.view` on the route: a hidden item is 404 first, whatever the input). **publish**: approved to published by `intelligence.publish`; never the author, the owner or the approving reviewer (author, approver and publisher pairwise distinct; the owner too, since the owner can edit); from the version read; an `approve` review of the current version whose content hash matches the content recomputed under the row lock (anything changed since, however, means review again); confidential, restricted or high-impact items only by an active holder of the `ci_director` role (`UserDirectory::lockedHoldsRole`, under a share lock on their row; the role is named, not inferred from the permission, so a custom role with `intelligence.publish` publishes only internal or public, ordinary items); every claim still supported by available evidence (withdrawn since the approval: refused, review again). Sets `released_at`, writes a `publish` review row, audited `intelligence.published` (approval ULID, review ULID, version). **Supersession**: "Draft a replacement" on a published item (`intelligence.create`, the writer sees the item and its subjects) creates a draft with its title, summary, type, classification, impact, dates and subjects and `supersedes_id`; claims and evidence are added afresh and reviewed; audited `intelligence.replacement_drafted`. Publishing it supersedes the original in the same transaction (both rows locked in ID order), refused if the original is no longer published; audited `intelligence.superseded` on the original. **retract**: published to retracted by `intelligence.retract`, with a reason (plain text, at most 5,000 characters), optionally naming another published item the actor can see as its replacement (both rows locked in ID order); an append-only `retractions` row; audited `intelligence.retracted` (whether a replacement was named, version; never the reason). Retracted and superseded items stay readable to everyone who could read them, with a banner (reason, by whom, when, the replacement or successor if visible). The item page shows a director what still blocks publication. Not yet: `IntelligencePublished` / `Retracted` / `Superseded` events and the outbox (with their first consumer: search indexing, Phase 2), flags for re-review (P1-48).
- **Implemented (P1-45, 2026-11-07):** the provenance view, `GET /intelligence/{item}/provenance` (`ProvenanceController`; linked from the item page), for anyone who sees the item (404 otherwise): the item's dates and the SHA-256 of its content now, compared with the current version's approval ("matches" or "changed after it was approved"); each claim with the evidence it cites as the viewer may see it (Evidence contract `EvidenceProvenance::traces`: `evidence.view`, then `EvidenceAsset::seenBy`), each citation with its relation, locator and excerpt, the asset's stored content (SHA-256, type, size, integrity), the source and policy version recorded at capture (`SourceLookup::recorded`; a source the viewer cannot see is a placeholder) and the chain of custody; evidence the viewer cannot see is counted per claim, never described (docs/07 §3; with P1-36b, the provenance hiding); the reviews with their versions and content hashes, the retraction, and the items it replaces or that supersede it (named only when visible). For `audit.view` holders, the item's audit trail (`AuditEvent::visibleTo`; a bounded snapshot of its first 200 events, then a link to the audit log filtered by the item; every `*_ulid` context value that names something the viewer does not see on the page is shown as `hidden`, TASK-0092 #1); showing it is audited as `intelligence.provenance_viewed` (rows shown), as an audit search is. The evidence page now shows the SHA-256 and the intelligence citing the asset (Intelligence contract `IntelligenceCitations::forEvidence`): items the viewer sees, with the relations, are named; the others counted.
- **Implemented (P1-48, 2026-11-07; PO decisions 2026-11-07: both triggers built now, and the item keeps its status with a flag rather than moving to in_review):** flags for re-review. The Evidence outbox events `evidence.withdrawn` and `evidence.integrity_failed` (`Modules\Evidence\Events\EvidenceEvents`; payload: the asset's ULID) are the first outbox events with a consumer: `FlagCitingItems` (Intelligence), run by the relay in a transaction with its receipt, locks the approved or published items whose claims (not withdrawn) cite the asset with any relation, in ID order, and writes one append-only `rereview_flags` row per item, asset and cause, sets `intelligence_items.rereview_since` if the item had no open flag, and audits `intelligence.rereview_flagged` (cause, evidence ULID, flag ULID, version; by the system). Nothing changes status and nothing is retracted (O13): a published item stays readable to everyone who could read it, with an "Under re-review" banner listing the flags (the evidence named only to viewers who can see it); a flagged item cannot be published. **clearRereview** (`POST /intelligence/{item}/rereview/clear`; only `intelligence.view` on the route, a hidden item is 404 first): `intelligence.publish`, the Director role for confidential, restricted or high-impact items, never the author or owner, from the version read, a reason (plain text, at most 5,000 characters), and only if every claim not withdrawn is still supported by available evidence the director can see (otherwise retract it or draft a replacement); a `clear_rereview` review row with the rationale; audited `intelligence.rereview_cleared` (review ULID, open flags, version). A later failure flags the item again; only flags raised since `rereview_since` are open. The provenance view lists every flag, open or cleared. "Available" support (submit, approve, publish, clear, citing) now also requires the evidence's stored bytes to have passed their integrity check. ### Evidence scanning (P1-32b)

Evidence uploads dispatch `ScanEvidenceJob` only after the upload transaction commits. The job uses the in-house Platform clamd client over the private data network. ClamAV errors are retryable and never treated as clean. Clean content is deduplicated into the locked `evidence` bucket; infected content and content whose magic-byte type no longer matches the upload extension are rejected and their quarantine object is removed. Audit and custody records contain codes and system actors only.
